# `.deck` Bundle Format Specification

**Status:** Canonical v2 spec (2026-08-28). `contentSchemaVersion: "2.0.0"` is the
current authoring format for newly created decks.
Companion specs: `system-architecture.md`, `project-overview-pdr.md`.

This document defines the v2 content schema only. Decks stamped with
`contentSchemaVersion: 1.x` (or with the field absent) remain on the supported,
frozen v1 schema and keep their legacy parser and validator behavior unchanged.
V1 is not extended or automatically migrated; this document deliberately does
not redefine it.

## 1. What a `.deck` is

A `.deck` is a **folder bundle** — the portable, self-contained unit of one presentation. It is git-diffable, zippable for sharing, and readable/editable by both the agent and the CLI. It contains authored content, a structured manifest, and local assets. Generated artifacts (React source, exports) are regenerable and kept out of the canonical bundle.

## 2. Layout

```text
my-talk.deck/
├── deck.json         ← manifest (structured, machine-owned)
├── content.md        ← authored content + annotations (human/agent-owned)
├── schema-guidance.md ← thin local schema/template editing guardrails
├── assets/           ← images, icons overrides, fonts, generated graphics
├── template/         ← embedded snapshot of the used .template (pinned; portability)
└── .build/           ← OPTIONAL, generated, git-ignored (source/, export/)
```

- **Canonical (commit + share):** `deck.json`, `content.md`, `assets/`, and the
  pinned `template/` snapshot when present.
- `schema-guidance.md` is scaffolded for new decks. Legacy bundles that predate
  it remain valid, but `aideck doctor` reports the missing/stale local file and
  `aideck guidance sync` deterministically backfills it from `deck.json`.
  Retemplating refreshes it after the template binding changes.
- **Generated (disposable):** `.build/` (React source + HTML/PDF export). Regenerated by `aideck serve`/`export`.

## 3. `deck.json` manifest

Promotes the current `.slides.md` frontmatter to a structured, validated file. The CLI owns it; the agent may read it but edits content in `content.md`.

```json
{
  "schema": "ai-deck-kit/deck@1.0.0",
  "title": "Presentation title",
  "slug": "my-talk",
  "audience": "Who this is for",
  "goal": "What the presentation should achieve",
  "template": { "set": "swiss-modern", "version": "2.0.0" },
  "slideTypeCatalog": "v1",
  "blockCatalog": "v1",
  "contentSchemaVersion": "2.0.0",
  "outputMode": "react-and-static-html",
  "status": "draft",
  "defaults": { "animation": "gentle-rise", "transition": "none" },
  "slides": [
    { "id": "slide-01", "type": "title", "file": "content.md#slide-01" }
  ],
  "generation": { "source": "prompt|document|outline", "params": {} }
}
```

- `slides[]` is the ordered slide registry (source of truth for order + type). Reordering = reorder this array (via `aideck slide move`).
- Slide ids following the numeric convention (`slide-01`, `slide-02`, …) are position-derived: `aideck slide add|move|remove` renames them to match their new 1-based position, and re-syncs `slides[].file`, the section YAML `id`, and the `## Slide NN (slide-NN)` heading label to match. A slide's numeric id is therefore an address, not a durable handle — it can name a different slide after any reorder. Custom, non-numeric ids (`slide-summary`) are never renamed; use one when a slide needs an identity that survives reordering.
- `template.set` + `template.version` bind the deck to exactly one template set.
- The four version axes (`template.version`, `slideTypeCatalog`, `blockCatalog`, `contentSchemaVersion`) mirror the current system.

## 4. `content.md`

`content.md` is Markdown with one YAML metadata fence per slide. The slide
heading is a structural boundary only: it carries no title or other semantic
data. `id`, `type`, and `title` come from the YAML fence, and the section id
must match a `deck.json` `slides[].id`.

````markdown
## Slide 05 (slide-05)

```yaml
id: "slide-05"
type: "content-text"
layoutVariant: "two-column"
status: "draft"
intent: "One-line authoring intent, not shown on slide"
animation: "gentle-rise"
transition: "none"

title: "How the idea plays out in practice"
description: "Optional supporting line."
kicker: "Concept vs. application"
leftTitle: "Concept"
rightTitle: "Application"
items:
  - column: "left"
    title: "Prompt structure"
    description: "..."
    icon: "target"
  - column: "right"
    title: "Campaign brief"
    description: "..."
    icon: "folder-open"

override:
  layout: "none"
  animation: "none"
  css: ""
  html: ""
  reason: ""

assets: []
```

### Speaker Notes
What the presenter says; not on the slide.

### Design Notes
Layout / hierarchy / spacing constraints.

### Review Questions
- Unresolved question for this slide.
````

For v2 decks, `title:` in YAML is the sole title source. There is no fallback to
text after the heading. `description:` is the authoring key for the existing `body`
render prop. List/card data always uses `items[]` entries with this shape:

```yaml
items:
  - title: "Required visible label"
    description: "Optional supporting copy"
    icon: "optional-phosphor-name"
    column: "left" # optional; only "left" or "right"
```

`items[].icon` replaces a flat positional `icons[]` array. Two-column layouts
filter the one canonical array by `column`; the parser does not create
`leftItems` or `rightItems`. Layouts that only need labels/icons may accept an
item description and ignore it; the per-type table below calls out those cases.

Templates may also declare optional presentation fields in the slide metadata:
`layoutVariant`, `backgroundVariant`, `highlightPhrase`, `courseName`,
`lessonName`, and `sectionName`. These remain template-owned and absent-safe.
If present, `layoutVariant` and `backgroundVariant` must exist in the selected
template manifest. The runtime supplies current/total page position.

Structured fields stay explicit rather than being folded into `items[]`:
`images[]`, `stats[]`, `chartData[]`, `regionSeries[]`, `tableColumns`, and
`tableRows`. Code slides keep `language` as documentation metadata even though
the current tokenizer does not branch on it. `blocks[]` and `morph` remain the
separate design-primitives mechanism described below.

### Field reference by slide type

The following table is the authoring reference for the clarity-courseware
slide catalog. Every row lists fields beyond the always-present `title`.

| Type | Variants | Fields beyond `title` | Notes |
|---|---|---|---|
| `title` | image-statement | `imageSrc`, `imageAlt`, `courseName`, `lessonName`, `highlightPhrase` | No `description`/`items`. |
| `section-divider` | number-led | `index`, `description` | |
| `content-text` | statement(-orange) | `kicker`, `description`, `source`, `caption` | |
| `content-text` | statement-plain(-orange) | `caption` | `kicker`/`description` are ignored; omit them when authoring. |
| `content-text` | list-vertical, list-horizontal | `kicker`, `description`, `items[]` (title/description/icon) | 3–5 items. |
| `content-text` | two-column | `kicker`, `description`, `leftTitle`, `rightTitle`, `items[]` with `column` | Up to 3 items per side. |
| `content-media` | figure-left/right | `kicker`, `description`, `imageSrc`, `imageAlt` | `description` supports literal `\n`. |
| `content-media` | image-grid-left/right | `kicker`, `description`, `images[]` (src/alt/caption) | 2–5 images. |
| `full-bleed-image` | editorial-overlay(-white), caption-strip(-black) | `kicker`, `description`, `imageSrc`, `imageAlt` | |
| `table` | reference-table | `kicker`, `tableColumns`, `tableRows` | Maximum 5×6. |
| `table` | comparison-table | plus `recommendedColumn` (0-indexed) | |
| `code` | explain-and-code | `kicker`, `description`, `code`, `language`, `highlightLines` | `language` is documentation-only today. |
| `code` | focus-lines | `code`, `highlightLines` | No `kicker`/`description`/intro title. |
| `data-visual` | metric-highlight | `kicker`, `metric`, `metricLabel`, `imageSrc`, `items[]` | `metric`/`metricLabel` fall back to `title`/`description` if omitted. |
| `data-visual` | stat-cards(-orange) | `description`, `stats[]` (value/label) | |
| `data-visual` | comparison-chart, pie-chart | `kicker`, `description`, `chartData[]` (label/value) | |
| `data-visual` | region-chart | `description`, `regionSeries[]` (name + data[]) | |
| `data-visual` | concept-diagram | `kicker`, `description`, `items[]` (title, optional icon) | Maximum 4 nodes. `items[].icon` overrides the auto-guess; item `description` is accepted but unused. |
| `quote` | centered-quote(-black) | `attribution` | `title` is the quote text. |
| `quote` | pull-quote(-black) | `attribution`, `kicker`, `description` | `kicker` defaults to “Context”. |
| `closing` | next-steps | `kicker`, `description`, `items[]` (title, optional icon) | Maximum 4. Item `description` is accepted but unused. |
| `closing` | final-statement | `kicker`, `description` | |

The engine's shipped linear-dark template also supports its technical slide
catalog. Its additional structured fields remain template-owned; they follow
the same rule of one YAML source field per rendered value and are not encoded
as heading prose.

### Annotation policy (reused)

Speaker Notes / Design Notes / Review Questions carry forward the existing in-content annotation approach (`engine/skills/presentation-crafting/references/annotation-policy.md`). This is the "annotation" module — no new mechanism invented.

### Blocks & morph (design-primitives layer)

Slides compose shared **block types** from the primitives layer. Prose blocks stay free-form in the sections above; **structured/data blocks** (chart, table, stat) and **morph anchors** are declared explicitly so they render deterministically and can animate across slides.

```yaml
# inside a slide's yaml block
blocks:
  - type: "chart"          # from block-catalog v1
    id: "revenue-chart"
    morph: "revenue"       # shared anchor: morphs to the block with morph:"revenue" on another slide
    data:
      kind: "bar"
      series: [ { label: "Q1", value: 10 }, { label: "Q2", value: 18 } ]
  - type: "stat"
    id: "arr"
    data: { value: "$1.2M", label: "ARR" }
```

- `blocks[].type` must exist in the declared `blockCatalog`.
- `morph` anchors with the same name on consecutive slides tween between states in the runtime.
- Prose-only slides need no `blocks:` list; the template renders the section prose via default blocks.

## 5. Field ownership

| Field / area | Owner | Edited via |
|---|---|---|
| `deck.json` structure, slide order/type | CLI | `aideck new`, `slide add/remove/move`, `anim/transition` |
| `title`, `description`, `items`, table/image/chart fields, notes, and annotations | Agent/human | `content.md` |
| `assets/` | Agent/human/CLI | file ops / generators |
| `.build/` | CLI | `serve`, `export` |

Invariant: order + type live in `deck.json`; prose + intent live in `content.md`. Keep them in sync — CLI slide ops update both.

## 6. Validation

The following is the validation contract for this schema. The
canonical `validate-slide-content.mjs` implementation (and `aideck validate`,
which wraps it) now dispatches on the major of the deck's
`contentSchemaVersion`: a `1.x` deck is judged by its frozen legacy rule set
and must pass exactly as it always has; a `2.x` deck is judged by the rules
below. No deck migration exists or is planned — existing decks stay on v1
indefinitely.

`aideck validate <deck>` (wrapping the canonical
`validate-slide-content.mjs` logic) enforces:

- every `deck.json` slide has a matching `content.md` section and vice-versa;
- every `type` exists in the declared `slideTypeCatalog`;
- required per-slide fields present (`id`, `type`, `status`, `intent`, `animation`);
- every `items[]` entry has a non-empty `title`;
- every `items[].column`, when present, is `left` or `right`;
- `override.reason` is non-empty when any of `override.layout`, `override.animation`, `override.css`, or `override.html` is set;
- `override.css` must not contain an unescaped `</style>` and `override.html` must not contain `<script`;
- every `items[].icon` value resolves to a real export from `@phosphor-icons/react` (kebab-case or PascalCase); unknown values fail validation with the slide and value named;
- every `blocks[].type` exists in the declared `blockCatalog`; data blocks carry required structured fields;
- `morph` anchors resolve to a matching anchor on an adjacent slide;
- an embedded template snapshot, when present, has the same name, version, and
  slide-type catalog as `deck.json`; otherwise `template.set`/`version` resolves
  to an installed `engine/templates/<name>.template` set.

V1-to-v2 conversion is not part of `aideck upgrade`. It is an explicit,
user-requested, agent-operated workflow owned by the engine's
`content-schema-migration` skill. The agent works on a copy, migrates a
compatible template and content together, validates and visually compares both
versions, and waits for approval before replacing canonical files.

## 7. Migration from current layout

The historical `working-files/{slug}/` layout maps to `decks/{slug}.deck/` as
follows. This describes the bundle layout; it is not an automatic v1 content
migration:

- `content/{slug}.slides.md` → `content.md`; frontmatter → `deck.json`.
- `assets/` → `assets/`.
- `source/`, `export/` → `.build/` (regenerable; not canonical).

## 8. Portability & sharing

- Move/copy the `.deck` folder between projects/users — its embedded template
  snapshot is the first preview source; an installed matching set is the
  fallback when no snapshot is present.
- `aideck pack <deck>` → `<deck>.zip` for sending; `aideck unpack` restores it.
- If the recipient lacks the template set, `aideck doctor` reports the missing `template.set@version`.

## 9. Templates as `.template` bundles (separate artifact)

Template sets are their own folder-bundle artifact — **`*.template`** — kept
separate from decks so the two evolve/upgrade independently. Project-authored
templates live in `templates/*.template/`; shipped defaults live in
`engine/templates/*.template/` and are replaced wholesale on engine upgrade.

- **Embed-when-used:** when a deck uses a template, a resolved copy is **embedded into the `.deck`** (e.g. `my-talk.deck/template/`) so the deck stays portable and renders even if the recipient lacks that template installed. `deck.json.template` records `set` + `version`; validation requires the embedded manifest's name and version to match that pinned identity.
- `aideck template ...` commands manage `.template` bundles; `aideck new` embeds the chosen template into the new deck.
- `.template` bundle = `template-manifest.json` (manifest: tokens ref, slide-type→layout map, block/motion catalogs, versions) + `design-system.css` + `layouts/` + `animation-presets.css` + `icon-policy.md`.

## Decisions (locked)

- Slide headings are structural only; YAML `title:` is the sole title source, including quote text.
- Card/list data uses one object-array `items[]` shape with optional `description`, `icon`, and `column`.
- `description` maps to the existing `body` render prop; no `body` authoring key is read.
- `css` and `html` extend the existing `override:` object beside `layout`, `animation`, and `reason`.
- `### On-Slide Text` and `### Visual Direction` are removed; explicit fields are the source of visible data and design intent.
- `stats[]`, `images[]`, `chartData[]`, `regionSeries[]`, `tableColumns`, and `tableRows` retain distinct shapes.
- `data-visual` concept diagrams accept `items[].icon` before their semantic-icon guess.
- `language` remains documentation-only metadata for code slides.
- `.build/` lives inside the bundle, git-ignored. No remaining open questions.
